## 0. 이 문서의 사용법

이 문서는 단순 기능 소개서가 아니라, 실제 구현 상태에 맞춰 작성한 **발표자용 대본·PPT 제작 지시서·라이브 시연 큐시트**입니다.

- 슬라이드에는 결론과 숫자만 남기고, 세부 설명은 발표자가 말합니다.
- 구현되지 않았거나 검증되지 않은 효과를 완료된 사실처럼 말하지 않습니다.
- “AI가 결정한다”가 아니라 **데이터가 후보를 좁히고 담당자가 최종 판단한다**고 설명합니다.
- “실시간 API”라는 표현은 현재 화면의 필터·재계산 반응을 설명할 때만 사용합니다. 현재 시연 데이터는 수집·정제·캐시된 JSON을 중심으로 동작합니다.
- 아래의 `검증된 사실`, `주의해서 말할 내용`, `시연 예상 결과`를 발표 전날 다시 대조합니다.

## 1. 발표에서 사용할 검증된 사실

### 1-1. 데이터 규모

| 데이터 | 현재 파일 기준 | 발표 표현 |
|---|---:|---|
| 상상대로 서울 시민 제안 | **824건** | 시민 정책 수요 |
| 국민신문고 민원 | **582건** | 현장 고충 신호 |
| 몽땅정보통 공식 사업 | **322건** | 기존 정책 공급 |
| 뉴스 기사 | **1,145건** | 사회 이슈·보도 신호 |
| 자치구 공공통계 | **25개 자치구** | 출생·보육 지역 지표 |
| 정책 갭 진단 | **57개 문제 군집** | 의사결정 후보 단위 |

### 1-2. 시민 제안 데이터 품질

| 항목 | 현재 값 | 해석 |
|---|---:|---|
| 전체 제안 | 824건 | 분석 모수 |
| 상세 본문 확인 가능 | **439건** | 제목과 구분되는 상세 본문 |
| 제목 수준 대체 본문 | **385건** | 상세 원문이 충분하지 않은 레코드 |
| 자치구 미상 | **804건** | 특정 자치구 실적으로 임의 배정하면 안 됨 |
| 자치구 확인 | 20건 | 원 데이터에 지역값이 있는 레코드 |
| 답변 완료 | 64건 | 화면 데이터 기준 |
| 미답변 | 760건 | 화면 데이터 기준 |

### 1-3. 정책 분류와 R&R 구조

- 제안은 **8대 정책 대분류 → 중분류 → 세분류**로 탐색합니다.
- 상단 첫 번째 선택기는 조직명이 아니라 **8대 정책 대분류 담당군**입니다.
- 상단 두 번째 선택기는 원본 업무분장에 근거한 **실제 R&R 팀**입니다.
- 전체 담당군에서 실제 팀을 선택하면 그 팀이 **1·2·3순위 어디에든 포함된 안건**을 찾습니다.
- 특정 대분류 담당군을 먼저 선택한 뒤 실제 팀을 고르면 그 대분류 안에서 **1순위 주관팀 안건만** 찾습니다.
- 현재 데이터의 실제 팀명은 14종이며, 각 제안에는 1순위 주관부서와 2·3순위 협조부서 후보가 저장됩니다.
- R&R은 공식 배정 확정이 아니라 **업무분장 근거를 보여주는 검토 후보 순위**입니다.

### 1-4. 발표에서 과장하지 않을 내용

- “824건 본문을 100% 복원했다” → 사용 금지.  
  **“439건은 상세 본문을 확인할 수 있고, 385건은 부족함을 표시한다”**고 말합니다.
- “18개 부서를 완벽히 자동 배정했다” → 사용 금지.  
  **“원본 업무분장 기반 1·2·3순위 R&R 후보를 제시한다”**고 말합니다.
- “업무 시간이 15분에서 15초로 70% 감소했다” → 계산도 틀리고 검증도 안 됨.  
  **“향후 실무 사용자 테스트에서 과업시간과 정확도를 측정한다”**고 말합니다.
- “진짜 HWP/PDF 바이너리를 생성한다” → 사용 금지.  
  현재 HWP는 `.hwp.txt`, PDF 요약은 화면 미리보기·인쇄 흐름, 원자료는 CSV입니다.
- “프로덕션 최적화가 100% 완료됐다” → 사용 금지.  
  현재 빌드는 통과하지만, 대용량 데이터 청크 최적화는 후속 과제입니다.
- “AI가 정책을 결정한다” → 사용 금지.  
  **“AI·규칙 기반 초안을 담당자가 검토·수정·승인한다”**고 말합니다.

# 3. 슬라이드별 PPT 구성 및 상세 대본

## Slide 0. 시민의 목소리를 행정의 다음 행동으로

### PPT 화면

- 다크 네이비 배경.
- 중앙: `UKKKK`
- 부제: `Unified Key-Knowledge Kit for Kid`
- 한 줄 가치: **“파편화된 정책 수요를 담당 범위·근거·조치안으로 연결하는 서울시 출산·양육 정책 의사결정 대시보드”**
- 우측 하단: 머리 위에 새싹이 난 강아지 마스코트.
- 말풍선: “어떤 안건부터, 어느 팀이, 왜 봐야 하는지 안내할게요.”

### 발표 대본 — 20초

> 안녕하십니까. 시민 제안은 많지만, 그 안에서 어떤 문제를 먼저 보고 어느 팀이 검토해야 하는지는 여전히 담당자의 수작업에 의존합니다.  
> 저희 UKKKK는 흩어진 출산·양육 정책 데이터를 한곳에 모아 **시민 수요를 담당 범위와 근거, 다음 조치로 연결하는 행정 의사결정 대시보드**입니다.

### PPT 화면

- 좌측: 김서현 주무관 카드.
- 우측: 브라우저 탭, 엑셀, 시민 제안, 부서 연락망, 보고서가 흩어진 장면.

### 발표 대본 — 35초

> 저희가 설정한 핵심 사용자는 정책업무에 배치된 지 6개월 된 김서현 주무관입니다.  
> 서현 주무관은 시민 제안을 읽고 소관팀과 협조팀을 찾고, 기존 정책과 민원·뉴스 근거를 대조한 다음 보고자료까지 만들어야 합니다.  
> 문제는 한 제안이 여러 업무에 걸치고, 데이터는 서로 다른 파일과 사이트에 있으며, 본문이나 자치구 값이 없는 경우도 많다는 것입니다.  
> 그래서 사용자의 질문을 하나로 정의했습니다. **“이 안건은 누가, 왜, 얼마나 먼저 봐야 하는가?”**

## Slide 2. AS-IS: 데이터와 책임이 따로 움직인다

### PPT 화면

좌측 `AS-IS`:

1. 제안·민원·사업·뉴스·통계를 각각 검색
2. 제목을 읽고 수작업으로 분류
3. 조직도와 업무분장표에서 소관팀 탐색
4. 기존 사업 존재 여부를 다시 검색
5. 보고서에 수치를 재입력

우측에 3개 위험:

- **누락**: 반복 수요를 놓침
- **혼선**: 대분류와 실제 조직을 혼동
- **근거 단절**: 추천 조치의 이유를 추적하기 어려움

### 발표 대본 — 35초

> 기존 업무는 다섯 단계를 여러 창에서 반복합니다. 제안을 찾고, 제목과 본문을 읽어 분류하고, 조직도에서 담당팀을 찾고, 기존 정책을 다시 검색한 뒤 수치를 보고서에 옮깁니다.  
> 이 과정에서는 반복 민원이 묻히거나, 정책 대분류를 실제 조직명으로 오해하거나, 왜 이 안건이 우선인지 근거가 끊길 수 있습니다.  
> 핵심 문제는 데이터 부족만이 아니라 **수요와 책임, 근거와 조치가 연결되지 않는 것**입니다.

## Slide 3. TO-BE: 한 화면에서 근거와 R&R까지

### PPT 화면

한 줄 흐름:

`범위 선택 → 수요 발견 → 원문 확인 → 기존 정책 대조 → 갭 진단 → 담당자 승인 → 보고서`

핵심 가치 3개:

- **찾기**: 8대 정책 대분류와 실제 팀의 2단계 범위 선택
- **판단하기**: 수요·공백·시급성·실행성·신뢰도
- **넘기기**: 검토·승인 로그와 범위가 반영된 보고서

### 발표 대본 — 25초

> UKKKK는 이 과정을 하나의 흐름으로 바꿉니다.  
> 먼저 정책 대분류와 실제 R&R 팀으로 업무 범위를 정하고, 반복 수요와 원문을 확인합니다. 다음으로 기존 사업과 민원·뉴스·통계를 대조해 공백을 판단하고, 담당자가 초안을 수정·승인한 뒤 같은 범위로 보고서를 내보냅니다.  
> 자동화의 목적은 결정을 대신하는 것이 아니라 **담당자가 더 빨리 검증 가능한 결정을 내리게 하는 것**입니다.

## Slide 4. 5원 데이터 융합 구조

### PPT 화면

5개 입력 노드:

1. 상상대로 시민 제안 **824**
2. 국민신문고 민원 **582**
3. 몽땅정보통 공식 정책 **322**
4. 뉴스 **1,145**
5. 25개 자치구 공공통계

가운데 처리:

`정규화 → 8대 분류 → 문제 군집 → R&R 후보 → 근거 연결`

하단 문구:

**“수요만 보지 않고, 현장·공급·사회 신호·지역 조건을 함께 본다.”**

### 발표 대본 — 40초

> 데이터는 다섯 출처를 결합했습니다. 상상대로 시민 제안 824건은 정책 수요, 국민신문고 582건은 현장 고충, 몽땅정보통 322개 사업은 기존 공급, 뉴스 1,145건은 사회적 이슈, 자치구 통계는 지역 조건을 보여줍니다.  
> 현재 데모는 이 데이터를 미리 수집·정제해 캐시한 구조로 안정적으로 재현됩니다.  
> 이후 텍스트 정규화와 계층 분류, 의미 유사 군집화, R&R 후보 매칭을 거쳐 화면에서 서로 대조합니다.  
> 즉, 제안 건수 하나만으로 판단하지 않고 **수요·현장·공급·사회·지역 근거를 함께 보는 구조**입니다.

### 발표자 주의

- “모든 데이터가 발표 순간 API로 새로 수집된다”고 말하지 않습니다.
- `실시간`은 필터와 화면 재계산, 사용자 조작 반응을 설명할 때 사용합니다.

## Slide 5. 두 단계 담당 범위 선택

### PPT 화면

```text
1단계 정책 담당군
전체 또는 8대 정책 대분류
        ↓
2단계 실제 R&R 팀
원본 업무분장 기반 팀명
```

두 가지 동작을 나란히 표시:

| 선택 방식 | 검색 의미 |
|---|---|
| 전체 담당군 + 실제 팀 | 해당 팀이 1·2·3순위 어디에든 포함된 안건 |
| 특정 담당군 + 실제 팀 | 해당 대분류에서 그 팀이 1순위 주관인 안건 |

우측에 제안 카드:

# 5. 예상 질문과 답변

## Q1. 8개 담당군이 실제 서울시 부서입니까?

> 아닙니다. 첫 번째 선택기의 8개 담당군은 정책 수요를 묶는 대분류입니다. 실제 조직과 업무분장은 두 번째 실제 R&R 팀 선택기와 제안별 1·2·3순위 카드에서 별도로 보여줍니다.

## Q2. 한 팀이 여러 담당군에 왜 겹칩니까?

> 출산·양육 정책은 대상과 업무가 겹치기 때문에 한 팀이 여러 분야의 주관 또는 협조 후보가 될 수 있습니다. 중복을 제거하는 대신 전체 담당군에서는 1·2·3순위 관련 안건을 찾고, 특정 담당군에서는 1순위 주관 안건만 보도록 검색 의미를 분리했습니다.

## Q3. R&R 추천이 틀리면 어떻게 합니까?

> 자동 확정이 아니라 업무분장 근거를 제공하는 후보 랭킹입니다. 담당자는 업무 요약과 전화번호, 주관·협조 순위를 확인하고 최종 판단합니다. 오매칭 신고와 승인 이력은 통합 로그에 남깁니다.

## Q4. 본문이 없는 제안은 어떻게 처리합니까?

> 제목을 상세 본문처럼 반복하지 않습니다. 현재 385건은 상세 본문이 충분하지 않은 상태로 표시하며, 원문 URL과 수집 상태를 확인할 수 있도록 합니다.

## Q5. 자치구 미상 804건이면 지역 분석이 왜 필요합니까?

> 시민 제안 수만으로 자치구 수요를 단정하지 않습니다. 자치구 비교는 출생아수, 합계출산율, 보육시설 등 공공통계를 중심으로 보고, 지역이 확인된 제안만 보조 근거로 사용합니다. 텍스트 기반 복원도 확실한 지명만 후보로 제시하고 사람이 검토합니다.

## Q6. 정말 실시간입니까?

> 현재 데모는 안정적인 재현을 위해 수집·정제한 캐시 데이터를 사용합니다. 화면의 필터링과 지표 재계산은 즉시 반영됩니다. 실제 운영 단계에서는 정기 수집 API, DB, 버전 관리가 추가로 필요합니다.

## Q7. AI가 답변을 자동 발송합니까?

> 아닙니다. Gemini 호출이 가능한 환경에서는 초안을 생성하고, 그렇지 않으면 대체 템플릿을 사용합니다. 어떤 경우에도 담당자가 검토·수정·승인하며 자동 발송하지 않습니다.

## Q8. HWP와 PDF를 바로 받을 수 있습니까?

> 현재 HWP는 행정 문체 텍스트 파일, PDF는 미리보기·인쇄용 요약 흐름, 원자료는 CSV입니다. 네이티브 HWP와 PDF 바이너리 생성은 운영화 단계의 과제입니다.

## Q9. 왜 57개 군집입니까?

> 개별 제안·민원을 정책 문제 단위로 비교하기 위해 현재 진단 데이터에서 생성된 문제 군집 수입니다. 군집 수는 고정된 행정 분류가 아니라 데이터와 군집 기준이 바뀌면 다시 검증해야 하는 분석 단위입니다.

## Q10. 도입 효과는 검증됐습니까?

> 기능 동작과 데이터 정합성은 확인했지만, 실제 업무시간 단축과 R&R 정확도는 아직 실무자 테스트 전입니다. 동일 과업의 기존 방식·대시보드 방식 비교로 시간, 오류, 수정률, 만족도를 측정할 계획입니다.
