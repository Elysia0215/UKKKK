> 발표 원칙: **문제 가설 → 가상 사용자 → 데이터 → 판단 구조 → 새싹이와 함께 보는 제품 흐름 → 라이브 시연 → 확인 범위와 한계**

---

## 0. 이 문서의 사용법

이 문서는 단순 기능 소개서가 아니라, 실제 구현 상태에 맞춰 작성한 **발표자용 대본·PPT 제작 지시서·라이브 시연 큐시트**입니다.

- 슬라이드에는 결론과 숫자만 남기고, 세부 설명은 발표자가 말합니다.
- 구현되지 않았거나 검증되지 않은 효과를 완료된 사실처럼 말하지 않습니다.
- “AI가 결정한다”가 아니라 **데이터가 후보를 좁히고 담당자가 최종 판단한다**고 설명합니다.
- “실시간 API”라는 표현은 현재 화면의 필터·재계산 반응을 설명할 때만 사용합니다. 현재 시연 데이터는 수집·정제·캐시된 JSON을 중심으로 동작합니다.
- 공무원의 현행 업무 절차를 직접 조사한 결과가 아니므로, **확인된 AS-IS가 아니라 제품 설계를 위한 업무 가설**이라고 설명합니다.
- 김서현 주무관은 실제 인물이 아니라 기능 시연을 위해 만든 **가상 페르소나**입니다.
- 아래의 `검증된 사실`, `주의해서 말할 내용`, `시연 예상 결과`를 발표 전날 다시 대조합니다.

### 1-2. 시민 제안 데이터 품질

| 항목 | 현재 값 | 해석 |
|---|---:|---|
| 전체 제안 | 824건 | 분석 모수 |
| 상세 본문 확인 가능 | **638건** | 화면 판정 기준 30자 이상 상세 본문 |
| 원문 미연결 또는 30자 미만 | **186건** | 원문 확인 또는 추가 수집이 필요한 레코드 |
| 원본 특정 자치구 | **20건** | 원 데이터에 자치구가 선택된 레코드 |
| 본문 특정 자치구 후보 | **49건** | 원본은 미상이지만 본문에 25개 자치구명이 직접 등장 |
| 서울시 전체 명시 | **5건** | `서울시 전체·서울 전역·전 자치구` 등이 직접 등장 |
| 지역 범위 미확인 | **750건** | 서울시 전체 요구와 판별 불가가 섞여 있어 추가 단정 금지 |
| 답변 완료 | 64건 | 화면 데이터 기준 |
| 미답변 | 760건 | 화면 데이터 기준 |

### 1-3. 정책 분류와 R&R 구조

- 제안은 **8대 정책 대분류 → 중분류 → 세분류**로 탐색합니다.
- 상단 첫 번째 선택기는 조직명이 아니라 **8대 정책 대분류 담당군**입니다.
- 상단 두 번째 선택기는 원본 업무분장에 근거한 **실제 R&R 팀**입니다.
- 전체 담당군에서 실제 팀을 선택하면 그 팀이 **1·2·3순위 어디에든 포함된 안건**을 찾습니다.
- 특정 대분류 담당군을 먼저 선택한 뒤 실제 팀을 고르면 그 대분류 안에서 **1순위 주관팀 안건만** 찾습니다.
- 현재 데이터의 실제 팀명은 14종이며, 각 제안에는 1순위 주관부서와 2·3순위 협조부서 후보가 저장됩니다.
- R&R은 공식 배정 확정이 아니라 **업무분장 근거를 보여주는 검토 후보 순위**입니다.

### 1-4. 발표에서 과장하지 않을 내용

- “824건 본문을 100% 복원했다” → 사용 금지.  
  **“638건은 상세 본문을 확인할 수 있고, 186건은 원문 미연결 또는 짧은 본문으로 표시한다”**고 말합니다.
- “18개 부서를 완벽히 자동 배정했다” → 사용 금지.  
  **“원본 업무분장 기반 1·2·3순위 R&R 후보를 제시한다”**고 말합니다.
- “업무 시간이 15분에서 15초로 70% 감소했다” → 계산도 틀리고 검증도 안 됨.  
  **“업무시간 단축과 추천 정확도는 검증하지 않아 성과 수치로 제시하지 않는다”**고 말합니다.
- “진짜 HWP/PDF 바이너리를 생성한다” → 사용 금지.  
  현재 HWP는 `.hwp.txt`, PDF 요약은 화면 미리보기·인쇄 흐름, 원자료는 CSV입니다.
- “프로덕션 최적화가 100% 완료됐다” → 사용 금지.  
  현재 빌드는 통과하지만, 대용량 데이터 청크 최적화는 후속 과제입니다.
- “AI가 정책을 결정한다” → 사용 금지.  
  **“AI·규칙 기반 초안을 담당자가 검토·수정·승인한다”**고 말합니다.
- 실제 기관의 업무 절차와 부담을 조사·검증한 것처럼 표현하지 않습니다.  
  **“제품 기능을 설명하기 위해 설정한 검토 흐름”**이라고 말합니다.

# 3. 슬라이드별 PPT 구성 및 상세 대본

## Slide 0. 시민의 목소리를 행정의 다음 행동으로

### PPT 화면

- 레트로 오피스 창 형태의 흰색 표지.
- 중앙: `UKKKK`와 `2차 발표 시작` 버튼.
- 부제: `Unified Key-Knowledge Kit for Kid`
- 하단 좌측: 손을 흔들며 발표 여정을 시작하는 새싹이.
- 실제 말풍선: **“모르는 값은 표시하고, 결정은 사람이 합니다.”**

### 발표 대본 — 20초

> 안녕하십니까. 저희는 4조 UKKKK입니다.  
> 원래 과제는 출산·양육 관련 민원과 데이터를 수집해 정책 수요를 도출하는 것이었습니다. 그런데 실제 ‘상상대로 서울’ 데이터를 확인하면서, 시민 제안의 답변 상태와 반복 수요, 실제 담당팀 후보, 기존 정책 근거가 한 흐름으로 연결되어 있지 않다는 점에 주목했습니다.  
> 그래서 저희는 상상대로 서울을 대체하는 서비스가 아니라, **시민 제안을 정책 검토와 후속 조치로 연결해 플랫폼의 활용을 돕는 백오피스**를 만들었습니다.  
> UKKKK는 시민 제안·민원·정책·뉴스·통계를 통합하고, 시민 수요를 담당 범위와 판단 근거, 다음 조치로 연결하는 행정 의사결정 지원 대시보드입니다.

## Slide 1. 페르소나: 신규 정책담당 김서현 주무관

### 페르소나

| 항목 | 내용 |
|---|---|
| 이름 | **김서현 주무관(가상 페르소나)** |
| 설정 | 서울시 여성가족 분야 정책업무 배치 6개월 차로 가정 |
| 가정한 과업 | 시민 제안 검토, 소관·협조 후보 확인, 기존 사업 대조, 보고자료 작성 |
| 시연 상황 | 월요일 오전, 출산·양육 제안 중 우선 검토 안건을 선별하는 상황을 가정 |
| 제품이 다루는 불편 | 데이터 탐색, 담당 후보 확인, 원문·지역 범위 검토가 분리될 때 생길 수 있는 연결 부담 |
| 목표 | “내가 볼 안건을 빠르게 좁히고, 왜 중요한지 근거를 확인한 뒤 보고서 초안까지 만든다.” |
| 성공 기준 | 범위 선택 오류 없이 관련 안건만 확인, 주관·협조 후보 구분, 원문·정책·민원 근거 확인, 결과 내보내기 |

### PPT 화면

- 상단 질문: **“월요일 오전, 무엇부터 봐야 할까요?”**
- 좌측 카드: 가정한 상황 — 출산·양육 정책 담당, 여러 출처 확인, 검토 우선순위 필요.
- 우측 카드: 필요한 지원 — 내 담당 범위 설정, 반복 수요·근거 확인, 보고자료 작성.
- 하단 좌측: 돋보기 새싹이.
- 실제 말풍선: **“실제 인물이 아닌 기능 시연용 가상 페르소나예요.”**

> 위 페르소나 표는 발표자 참고용 상세 설정입니다. 실제 슬라이드에는 표 전체를 넣지 않고, 현재 PPT와 같이 `상황 → 필요한 지원` 두 카드로 요약합니다.

### 발표 대본 — 35초

> 김서현 주무관은 실제 인물이 아니라 제품의 기능과 시연 과업을 구체화하기 위해 설정한 가상 페르소나입니다.  
> 시민 제안을 검토하고 담당 후보와 기존 정책 근거를 대조한 뒤 보고자료를 만든다는 과업을 가정했습니다.  
> 여러 정책 영역에 걸친 제안과 본문·지역 범위 미확인은 실제 데이터에서 확인했습니다. 담당자의 시스템 사용 방식과 업무 부담은 이번 분석 범위에 포함하지 않았으며, 가상 페르소나는 제품 기능과 시연 흐름을 설명하기 위한 설정입니다.  
> 그래서 사용자의 질문을 하나로 정의했습니다. **“이 안건은 누가, 왜, 얼마나 먼저 봐야 하는가?”**

## Slide 2. 검증할 업무 가설: 정책 수요 검토는 어디에서 단절되는가

### PPT 화면

화면 중앙 문구:

**“데이터는 있었지만, 수요와 책임·근거·조치가 끊겨 있었습니다.”**

- 화면은 중앙 문제 문장과 하단 새싹이 안내로 구성.
- 하단 좌측: 자를 든 새싹이.
- 실제 말풍선: **“실제 기관별 업무 절차를 대표한다고 단정하지 않아요.”**

### 발표 대본 — 35초

> 상상대로 서울에는 시민 제안이 축적되어 있지만, 제안만으로는 **어떤 수요를 먼저 살펴볼지, 어느 정책 영역과 실제 담당 후보가 연결되는지, 판단 근거와 다음 조치가 무엇인지**를 한 흐름에서 확인하기 어렵습니다.  
> 저희는 시민 수요와 정책·민원·뉴스·통계, R&R 근거를 연결해 이 단절을 보완하는 것을 제품이 다룰 문제로 정의했습니다.  
> 화면의 누락·혼선·근거 단절은 실제 기관의 확정된 업무 절차가 아니라, 수집 데이터와 제품 구조를 바탕으로 설정한 검토 위험입니다.

## Slide 3. TO-BE: 한 화면에서 근거와 R&R까지

### PPT 화면

- 좌측 `입력`: 시민 제안·민원, 정책·뉴스, 자치구 통계.
- 중앙 화살표.
- 우측 `출력`: 반복 수요·Gap, R&R 후보·원문, 맞춤 보고서·로그.
- 하단 좌측: 데이터를 정리하는 새싹이.
- 실제 말풍선: **“후보와 근거를 연결하고 최종 결정은 사람이 해요.”**

### 발표 대본 — 25초

> 화면의 왼쪽은 UKKKK가 받는 입력입니다. 시민 제안과 민원, 기존 정책과 뉴스, 자치구 통계를 한데 모읍니다.  
> 오른쪽은 그 데이터를 연결해 만든 출력입니다. 반복되는 수요와 정책 Gap, 주관·협조 R&R 후보, 원문 근거, 맞춤 보고서와 검토 로그를 제공합니다.  
> 즉, 이 화면은 실제 조작 순서를 설명하는 페이지가 아니라 **흩어진 입력을 검토 가능한 출력으로 바꾸는 제품의 역할**을 보여줍니다. 최종 판단과 승인은 담당자에게 남겨 둡니다.

## Slide 5. 두 단계 담당 범위 선택

| 특정 담당군 + 실제 팀 | 해당 대분류에서 그 팀이 1순위 주관인 안건 |

> 따라서 가족지원팀처럼 여러 분야에 협조로 참여하는 팀도 중복을 숨기지 않으면서, 사용자는 지금 ‘관련 안건 전체’를 보는지 ‘주관 안건’을 보는지 구분할 수 있습니다.

- “자동 배정”보다 **“R&R 후보 랭킹”**이라고 말합니다.
- 현재 R&R 랭킹은 카테고리·업무 키워드·기존 담당 후보를 결합한 **규칙·가중치 기반 모델**입니다.
- 1순위는 주관 후보, 2·3순위는 협조 후보입니다.
- 최종 배정 책임은 담당자에게 있습니다.

## Appendix B. 텍스트 전처리와 모델별 파싱 구조

### PPT 화면

| 처리 단계 | 입력·파싱 방식 | 출력 |
|---|---|---|
| 공통 전처리 | 조사·접미사 제거 → 도메인 유사어 통합 → 불용어 제거 | 정규화 토큰 |
| 계층 분류 | 제목·본문·원 카테고리의 규칙 키워드 점수와 원 분류 부스트 | 8대·중·소분류, 분류 신뢰도 |
| 의미 분류 | `snunlp/KR-SBERT-V40K-klueNLI-augSTS` 임베딩과 코사인 유사도 | 의미 카테고리, 유사도 점수 |
| 유사 제안 군집 | KR-SBERT 임베딩을 계층적 군집화(`cosine`, `average`, 거리 `0.25`) | `cluster_id`, `cluster_size` |
| 뉴스 파싱 | 규칙 분류 → 기존 8대 분류 → 수집 카테고리 → NMF 토픽 맵 순으로 보완 | 뉴스 대·중·소분류, 근거, 신뢰도 |
| 지역·R&R | 자치구 키워드와 모호어 감점 / 업무분장과 본문 토큰 가중치 대조 | 지역 후보·점수 / 주관 1순위·협조 2·3순위 |

새싹이 말풍선:

**“한 모델이 모두 결정하지 않아요. 단계마다 입력과 출력, 근거를 나눠 확인할 수 있어요.”**

### 발표 대본

> 텍스트 처리는 한 모델이 모든 값을 한 번에 예측하는 구조가 아닙니다. 먼저 한국어 조사와 접미사, 불용어를 제거하고 도메인 유사어를 통합합니다.  
> 계층 분류는 제목·본문·원 카테고리의 키워드 점수로 8대·중·소분류와 신뢰도를 만들고, KR-SBERT는 카테고리 설명과의 코사인 유사도로 의미 분류를 보완하며 유사 제안을 군집화합니다. 뉴스는 규칙 결과가 없을 때 기존 분류, 수집 카테고리, 이미 생성된 NMF 토픽 라벨을 순서대로 매핑합니다.  
> 마지막으로 자치구는 본문 키워드와 모호어 감점을 사용해 후보와 점수를 남기고, 실제 팀은 업무분장 원문과 제안 텍스트를 가중치로 대조합니다. 따라서 각 결과가 어떤 입력과 규칙에서 나왔는지 단계별로 추적할 수 있습니다.

# 5. 예상 질문과 답변

## Q1. 8개 담당군이 실제 서울시 부서입니까?

> 아닙니다. 첫 번째 선택기의 8개 담당군은 정책 수요를 묶는 대분류입니다. 실제 조직과 업무분장은 두 번째 실제 R&R 팀 선택기와 제안별 1·2·3순위 카드에서 별도로 보여줍니다.

## Q2. 한 팀이 여러 담당군에 왜 겹칩니까?

> 출산·양육 정책은 대상과 업무가 겹치기 때문에 한 팀이 여러 분야의 주관 또는 협조 후보가 될 수 있습니다. 중복을 제거하는 대신 전체 담당군에서는 1·2·3순위 관련 안건을 찾고, 특정 담당군에서는 1순위 주관 안건만 보도록 검색 의미를 분리했습니다.

## Q3. R&R 추천이 틀리면 어떻게 합니까?

> 자동 확정이 아니라 업무분장 근거를 제공하는 후보 랭킹입니다. 담당자는 업무 요약과 전화번호, 주관·협조 순위를 확인하고 최종 판단합니다. 오매칭 신고와 승인 이력은 통합 로그에 남깁니다.

## Q4. 본문이 없는 제안은 어떻게 처리합니까?

> 제목을 상세 본문처럼 반복하지 않습니다. 현재 186건은 원문 미연결 또는 30자 미만 상태로 표시하며, 원문 URL과 수집 상태를 확인할 수 있도록 합니다.

## Q5. 원본 자치구 미상 804건을 모두 결측치로 봅니까?

> 아닙니다. 원본 자치구 미상에는 서울시 전체에 대한 요구와 실제 지역 범위 판별 불가가 함께 포함됩니다. 원본 특정 자치구 20건, 본문 자치구명 복원 후보 49건, 서울시 전체 명시 5건을 구분하고, 나머지 750건은 지역 범위 미확인으로 유지합니다. 자치구 비교는 공공통계를 중심으로 보고 지역이 확인된 제안만 보조 근거로 사용합니다.

## Q6. 정말 실시간입니까?

> 현재 데모는 안정적인 재현을 위해 수집·정제한 캐시 데이터를 사용합니다. 화면의 필터링과 지표 재계산은 즉시 반영됩니다. 실제 운영 단계에서는 정기 수집 API, DB, 버전 관리가 추가로 필요합니다.

## Q7. AI가 답변을 자동 발송합니까?

> 아닙니다. Gemini 호출이 가능한 환경에서는 초안을 생성하고, 그렇지 않으면 대체 템플릿을 사용합니다. 어떤 경우에도 담당자가 검토·수정·승인하며 자동 발송하지 않습니다.

## Q8. HWP와 PDF를 바로 받을 수 있습니까?

> 현재 HWP는 행정 문체 텍스트 파일, PDF는 미리보기·인쇄용 요약 흐름, 원자료는 CSV입니다. 네이티브 HWP와 PDF 바이너리 생성은 운영화 단계의 과제입니다.

## Q9. 왜 57개 군집입니까?

> 개별 제안·민원을 정책 문제 단위로 비교하기 위해 현재 진단 데이터에서 생성된 문제 군집 수입니다. 군집 수는 고정된 행정 분류가 아니라 데이터와 군집 기준이 바뀌면 다시 검증해야 하는 분석 단위입니다.

## Q10. 도입 효과는 검증됐습니까?

> 기능 동작과 데이터 정합성은 확인했지만, 실제 업무시간 단축과 R&R 정확도는 검증하지 않았습니다. 따라서 시간 절감률이나 추천 정확도를 성과로 제시하지 않고, 현재 발표 범위를 기능 구현과 데이터 처리 기준으로 한정합니다.

## 8-2. EDA에서 확인한 실제 데이터 상태

| 확인 항목 | 현재 값 | 제품 설계에 반영한 결정 |
|---|---:|---|
| 시민 제안 | 824건 | 전체 정책 수요 분석 모수 |
| 답변 완료 / 미답변 | 64 / 760건 | 답변 여부를 우선순위 신호 중 하나로 사용 |
| 상세 본문 확인 가능 | 638건 | 본문 기반 키워드·분류·군집 분석 |
| 원문 미연결 또는 30자 미만 | 186건 | 제목 복제를 금지하고 수집 상태 표시 |
| 원본 특정 자치구 | 20건 | 원 데이터의 명시값만 확정 지역으로 사용 |
| 본문 자치구 후보 / 서울시 전체 명시 | 49 / 5건 | 직접 등장한 표현만 후보 또는 전체 범위로 구분 |
| 지역 범위 미확인 | 750건 | 서울시 전체와 판별 불가를 임의 분리하지 않음 |
| 정책 갭 분석 단위 | 전체 기준 57개 군집 | 개별 제안이 아닌 반복 문제 단위로 검토 |

발표 문장:

> EDA에서 가장 중요했던 결과는 지역값 `미상`을 모두 결측치로 취급할 수 없다는 점입니다. 원본 특정 자치구는 20건이고, 본문에 자치구명이 직접 등장하는 후보 49건과 서울시 전체 명시 5건을 분리했습니다. 나머지 750건은 전체 시 요구와 판별 불가가 섞여 있어 지역 범위 미확인으로 유지하고, 지역 비교는 공공통계를 중심으로 설계했습니다. 또한 본문이 확인되는 638건과 추가 확인이 필요한 186건을 분리해 화면 표시 기준을 달리했습니다.

## 8-3. 피처·분석 결과·검증 대상

| 구분 | 정의 |
|---|---|
| 입력 피처 | 제안·민원 건수, 공감·댓글, 답변 여부, 등록일, 본문 키워드, 정책 분류, 지역, 정책·뉴스·통계 근거 |
| 분석 결과 | 정책 대·중·소분류, 유사 문제 군집, Gap 5축 점수, 검토 우선순위, R&R 1·2·3순위 후보 |
| 사용자 출력 | 키워드·차트, 긴급 후보, 근거 패널, 답변 초안, 범위별 보고서·CSV |
| 최종 결정 | 담당자가 원문과 업무분장을 대조해 수정·승인·반려 |
| 후속 검증 | 군집 안정성, R&R 후보 정확도·수용률, 임계값 민감도, 보고서 수정률, 과업 시간·오류·만족도 |

> 현재 구현은 정답 라벨을 예측하는 감독학습 모델이 아니라, NLP·규칙·가중치 기반의 **분류·군집·우선순위·R&R 후보 추천 엔진**입니다. 따라서 발표에서도 ‘정책 자동 예측’보다 ‘검토 범위를 좁히는 의사결정 지원’으로 설명합니다.

## 8-4. KPI와 임계값 표현 원칙

- `30/25/25/10/10`은 기본 균형형 가중치입니다.
- 박미경(2022)형은 시민 수요를, KICCE(2023)형은 정책 공급 공백·지역 형평성을 상대적으로 강조합니다.
- 현재 가중치와 긴급 기준은 문헌과 제품 가설을 바탕으로 설정한 **운영 규칙**입니다.
- 실제 담당자 정답셋으로 최적화된 정확도나 정책 효과로 표현하지 않습니다.
- 발표 후 동일 데이터에 여러 임계값을 적용해 대상 건수와 순위 변화를 비교하는 민감도 분석이 필요합니다.

## 8-5. 기술 스택과 제작 도구

| 영역 | 실제 확인된 구성 |
|---|---|
| 프론트엔드 | React + TypeScript + Vite |
| 시각화·인터랙션 | Recharts, Motion, Lucide 아이콘 |
| 데이터 제공 | 수집·정제된 JSON 캐시와 공공통계 데이터 |
| 데이터 검사 | Python 동기화·정합성 검사 스크립트 |
| 생성형 AI | Gemini 답변 초안, 키 미설정·호출 실패 시 템플릿 Fallback |
| 배포 | Vercel |
| 상태·피드백 | 화면 상태와 localStorage 기반 승인·오매칭·복원 로그 |

제작 도구 표기 원칙:

- Stitch와 Antigravity는 제품 성능이나 분석 방법론이 아니라 **UI 탐색·구현 보조 도구**로만 소개합니다.
- Stitch 산출물은 실제 와이어프레임 파일 또는 캡처가 확인될 때만 발표 자료에 표시합니다.
- Antigravity는 프롬프트 또는 구현 이력이 확인되는 범위에서만 표기하며, 현재 엔진을 감독학습 ‘예측 모델’로 과장하지 않습니다.
- Gemini가 제안한 방법론은 코드·데이터·원 논문으로 다시 대조한 뒤 근거로 사용합니다.

산출물 확인 주의:

- 역할·일정 문서에는 `analysis/eda_analysis.ipynb`가 완료 산출물로 적혀 있으나 현재 저장소에서 해당 파일을 확인하지 못했습니다.
- 따라서 발표에서는 별도 EDA 노트북이 존재한다고 말하지 않고, 현재 확인되는 `데이터분석정의서.md`의 EDA 명세와 대시보드 수치만 근거로 사용합니다.
- 최종 제출 요건에 독립된 EDA 보고서나 노트북이 반드시 필요하다면 발표 전 별도 산출물로 생성해야 합니다.
