## 1. 프로젝트 배경 및 문제 정의 (Problem Statement)

### 🚨 현장의 문제점
* **데이터 파편화**: 공무원 실무자가 정책을 수립하거나 개선할 때, 시민들의 정책 제안(상상대로), 현장 민원(국민신문고), 기존 서울시 사업(몽땅정보통)이 각각 분산되어 있어 종합적인 상황 판단이 어렵습니다.
* **수요-공급 불일치**: 시민들의 고충이나 불만이 계속 제기됨에도 불구하고, 이것이 "신규 정책이 없어서"인지, "기존 정책의 홍보/신청 절차 문제"인지 명확히 파악하기 힘듭니다.
* **행정 소모도**: 수천 건의 파편화된 제안/민원 낱개 데이터를 일일이 열어보는 것은 과도한 행정력 낭비를 초래합니다.

## 2. 해결 방안: Multi-API 융합 수요-공급-민원 갭(Gap) 분석 시스템

본 시스템은 4가지 데이터 원천을 하나의 통합 8대 대분류 체계로 정규화한 후, **동일 주제별 [통합 이슈(Integrated Issue Card)] 단위로 묶어서 제공**합니다.

```
[ 1. 상상대로 시민제안 ] ➔ 시민이 바라는 "아이디어 / 정책 요구" (수요 824건)
[ 2. 국민신문고 민원 ]   ➔ 시민이 겪는 "현장 고충 / 불편 신호" (시급성 582건)
[ 3. 몽땅정보통 정책 ]   ➔ 공공이 제공 중인 "322개 현행 혜택" (공급 322건)
[ 4. 자치구 공공 통계 ] ➔ 서울시 25개 자치구 출생아수 & 보육시설 정원 (인프라 갭)
           ↓
 ── [통합 정책 분류 체계 (8대 대분류)] ──
           ↓
 ── [담당 부서 1·2·3순위 매칭 & 1클릭 일괄 행정 답변 공문 표출] ──
```

## 4. 메인 대시보드: 5대 퀵 카드 (Quick Board) 및 TOP 3 인사이트

1. **시민 수요 증가 이슈**: 공감수 및 제안 제출 건수가 급증하는 분야
2. **기존 정책 개선·홍보 필요 이슈**: 기존 사업이 존재하나 관련 불만 민원이 높게 발생하는 분야
3. **정책 공백 검토 이슈**: 시민 요구는 높으나 대응되는 몽땅정보통 정책이 적은 분야
4. **언론 확산 모니터링 이슈**: 사회적 보도 및 뉴스 언급량이 급증하는 분야
5. **부서 협업 검토 이슈**: 여성가족실, 시민건강국 등 다수 부서에 복합 연관된 분야

* **신규 TOP 3 인사이트 카드 탑재**:
  * 📦 **최다 제안 분야 TOP 3**: 1위~3위 정책 분야 목록 + 미니 프로그래스 바(게이지) + 비중(%) 표시 (클릭 시 해당 분야 데이터 필터링)
  * 📦 **최고 공감 제안 TOP 3**: 1위~3위 최다 공감 표 수(🔥 N표) + 제안 제목 목록 (클릭 시 제안 원문 팝업 모달)
* **HoverScrollText 전광판 스크롤**:
  * TOP 3 및 목록의 텍스트가 컨테이너 너비를 초과하면 마우스 호버 시 3초 정지 후 가로 스크롤(Marquee)되는 사용자 친화적 전광판 컴포넌트 탑재.

## 6. MVP 우선순위 점수 산식 (Scoring Model)

$$ \text{우선순위 점수} = (\text{수요강도} \times 0.4) + (\text{시급성} \times 0.3) + (\text{정책공백} \times 0.2) + (\text{뉴스확산} \times 0.1) $$

* **수요강도 (40%)**: 상상대로 제안 수 + 공감수 + 댓글수
* **시급성 (30%)**: 국민신문고 민원 수 + 안전/건강/위기 키워드 포함 여부
* **정책공백 (20%)**: 관련 몽땅정보통 정책 매칭 수가 적을수록 높게 가산
* **뉴스확산 (10%)**: 최근 보도량 및 이슈성 키워드

> 💡 **안전한 행정 표현 가이드**  
> * `"자동 확정/100% 판정"` 대신 ➔ **`"정책 공백 가능성 탐지"`, `"우선 검토 이슈 추천"`, `"설명 가능한 규칙 기반 매칭"`** 표현 사용  
> * 가중치(40-30-20-10)는 MVP 수식 예시이며 실무 피드백에 따라 유연하게 변경 가능한 구조입니다.

  - ③ **기존 정책 연결형**: 기존 유사 정책과의 연결·통합을 제안하는 공문
  - ④ **조례 개정 검토형**: 관련 조례 개정 검토를 요청하는 공문
  - 선택한 템플릿에 따라 공문 본문이 자동 생성됩니다.
- **미리보기 상시 표시**: 템플릿 선택 전에도 답변 미리보기가 항상 표시됩니다. 【】 변수가 포함되면 파란 뱃지로 시각 구분되며, 답변 수정 시 ⚠️ 수정됨 표시가 나타납니다.
- **수정 후 승인 강제 로직**: 담당자가 textarea에서 AI 답변 초안을 수정하면 `editedAnswer !== originalAnswer` 비교를 통해 "답변 승인" 버튼이 자동 비활성화(회색·cursor-not-allowed)되고 "수정 후 승인"만 활성화(노란 강조·pulse). AI 출력물 변경에 대한 Human-in-the-loop 거버넌스를 시스템적으로 보장합니다.
- **승인 이력 localStorage 영구 저장**: 승인·수정후승인·반려 피드백이 `approval_log` 키로 localStorage에 영구 저장됩니다. 저장 항목: issueId, cluster, actionType, aiOriginal, finalAction, wasModified, editedAnswer, reviewerId, timestamp. [결측치 복원 & 로그] 탭의 UnifiedLogViewer에서 교차 조회 가능.
- **신뢰도 산정 방법론 강화**:
  - **MCDA (Multi-Criteria Decision Analysis)** 기반 가중 점수 산정
  - **데이터 삼각검증(Data Triangulation)**: Denzin(2012) 논문 근거를 기반으로, 3개 이상 데이터 소스(제안/민원/정책)의 교차 확인을 통해 신뢰도를 산출합니다.
  - 신뢰도 등급: 상(3개 소스 일치) / 중(2개 소스 일치) / 하(단일 소스)
- **AI 정책 가설 자동 생성 엔진 (`getPolicyHypothesis`)**: 클러스터 선택 시 실제 시민제안·민원·정책 건수를 대입해 "이 정책이 왜 필요한지"를 학술 근거와 결합한 문장형 가설로 자동 생성. 카테고리별 분기(보육·돌봄/임신·난임/주거·노동 등)에 따라 가설 제목·본문·행정 액션·근거 지표(`{ title, body, action, metrics }`)를 반환. `metrics`는 수요 건수·정책 공백 점수·신뢰도·근거 논문 수 4개 배지로 표출됩니다.
- **🎓 4단계 학술 실증 검증 모달 (`getAcademicEvidenceItems`)**: 근거 논문 카드 클릭 시 팝업으로 **가설(Hypothesis) → 테스트(Test) → 실증 결과(Result) → 대시보드 이식 결론(Conclusion)** 4단계 검증 흐름을 표시. 6대 핵심 논문(성낙일·박선권 2012, KICCE 2023, 배기련 외 2021, 박미경 2022, 오신휘·김혜진 2020, NABO) 각각에 4단계 텍스트 사전 정의. `selectedEvidenceIndex` 상태로 근거 논문 상세 보기 패널 전환.

  - ④ **승인 이력(🔏)**: 정책 갭 진단 탭에서 답변 승인·수정후승인·반려한 의사결정 기록

```text
전역 범위
├─ 정책 대분류 담당군(8개)
└─ 실제 R&R 팀
   ↓
10개 사용자 화면
├─ 발견: 수요 현황 / 시민 목소리 / 긴급 민원
├─ 대조: 현행 정책 / 사각지대 / 자치구 통계

   ↓
새싹이 안내 · 보고서 빌더 · AI/개발 로그
```

## 11. 범위 상태와 필터 계약

- `departmentGroup`: 8개 정책 대분류 담당군. 조직명이 아니다.
- `rrDepartment`: 원본 업무분장 기반 실제 팀. 대분류 선택 시 관련 팀만 노출한다.
- 대분류만 선택한 상태의 화면은 해당 영역 전체를 집계한다.
- 실제 팀까지 선택하면 해당 팀이 1·2·3순위 후보 어디에든 포함된 안건을 범위로 한다.
- 화면별 필터는 전역 범위와 AND 조건으로 결합한다.
- 다중선택 OFF에서는 같은 행의 필터를 하나만 활성화하고, ON에서는 선택 집합을 합집합으로 처리한다.
- 필터 해제·초기화는 선택 상태뿐 아니라 종속 필터의 비활성·0건 상태도 복구한다.

## 13. AI·개발 로그 아키텍처

- 일반 사용자 테스트 피드백과 개발자용 AI 로그를 분리한다.
- 개발자 모드가 켜진 경우에만 로그 작성 버튼과 센터를 표시한다.
- 브라우저 `localStorage`를 즉시 캐시로 사용하고, 로컬 API가 실행된 환경에서는 `/api/developer-logs`로 파일 저장·병합한다.
- 배포 환경에서 API가 없더라도 로컬 캐시는 유지하고 JSON 내보내기를 지원한다.
- 동일 ID는 `updatedAt`이 최신인 레코드를 우선해 병합한다.
- 사용자가 근거 없이 상태만 전진시킨 구버전 이력은 유효 메모가 있는 마지막 상태로 복원한다.

상태는 `team_suggestion → ai_in_progress → ai_applied_data → ai_applied_rule → github_pushed` 순서이며, 각 단계는 실제 작업 메모와 수행 주체를 기록한다.

## 14. 비기능 요구사항과 안전장치
